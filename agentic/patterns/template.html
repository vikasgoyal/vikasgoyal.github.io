The pattern card

Every pattern in the library uses these nine sections in this order. Keeping the shape fixed lets readers compare patterns quickly and lets new cards be added without design work. Two finished examples: Fast/Slow Escalation and Evaluator–Optimizer.

Adding a pattern

Each pattern is one Markdown file in the _patterns/ folder of the site repo. The file name becomes the URL, so _patterns/draft-verify.md is published at {{ D.base }}draft-verify/. Change status: stub to status: full once every section is filled in.

Copied
---
title: Pattern Name
n: 40                     # catalog number, unique
family: core              # core | multi | context | safety | runtime | eval | fastslow
maturity: emg             # est | emg | hor
axes: [decision]          # decision | tool | context | verification | coordination
intent: One line, 20 words max.
aka: Other names, comma separated
status: full              # stub until every section is written

problem: >-
  The recurring situation, in one short paragraph.
forces:
  - Tension one, like latency vs. accuracy.
  - Tension two.
  - Tension three.

solution: >-
  How the pattern resolves the forces. Name the roles and decision points.

diagram: pattern-name     # _includes/patterns/diagrams/pattern-name.svg
diagram_caption: One fact about how it behaves in practice.

use_when:
  - A condition the reader can check.
avoid_when:
  - A condition where it does not fit.

tradeoffs:                # 1-5; same four on every card
  latency:     { score: 3, note: "…" }
  cost:        { score: 3, note: "…" }
  complexity:  { score: 3, note: "…" }
  reliability: { score: 3, note: "…" }
gains:
  - …
costs:
  - …

example:
  scenario: The concrete situation.
  steps:
    - who: User
      what: "What happens, with real values. `inline code` works."

failures:
  - failure: Name
    symptom: What you see
    fix: How to guard against it

related:                  # pattern = another file name, without .md
  - { type: Combines with, pattern: reflection }
